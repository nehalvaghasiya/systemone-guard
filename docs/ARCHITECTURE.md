# Architecture

The SystemOne Guard has 756,248 parameters. Its context encoder combines learned word embeddings with eight hashed character n-grams per word, local depthwise convolutions, three four-head attention layers, and attention/mean pooling. The encoder retains at most 160 context tokens, using the beginning and end of longer text. The synthetic policy treats typed state as authoritative, so request wording is excluded from the updated classifier; the public API retains the request field for compatibility.

The context encoder predicts source-independent instruction risk. Its detached probability vector and five categorical state embeddings feed the decision head. Sensitive/approval heads read state only; the attack head combines intent with source trust. All policy heads are learned networks. The private context label is supervised from synthetic training annotations and is never an inference input. Character features distinguish unfamiliar words rather than representing them all with one unknown vector. Ten-percent whole-word dropout during training encourages use of those subwords. All weights are trained from random initialization. Subword representations are motivated by [Bojanowski et al.](https://arxiv.org/abs/1607.04606); this is a custom supervised implementation, not fastText or a language-model encoder.

Four heads return logits simultaneously: a three-way allow/review/block decision and binary sensitive, approval-needed, and attack outputs. Validation-fitted temperature scaling calibrates the decision probabilities. The inference API preserves the same checkpoint and output schema on CPU or CUDA.

The comparison model is SmolLM2-135M-Instruct with a task-trained rank-8 LoRA adapter. It receives an explicit policy and the same public request/state fields, then generates four answer words. The adapter is merged into FP32 before inference. Constrained decision-token scores provide label probabilities; binary slots condition on previously decoded words. A separate free-generation diagnostic checks format compliance. Shared batching, probes, contracts, and reporting live under `benchmarking/`.

Guard trains on 90,000 examples and validates on 3,500 after broader context augmentation; frozen SmolLM2 LoRA retains its original 10,000/1,500 task data. Both use validation for checkpoint selection and temperature fitting. They differ in prior training, representation, objective, parameter count, and execution: Guard produces parallel heads in one pass, while SmolLM2 autoregressively decodes answer tokens. The benchmark includes all four outputs for both models and reports end-to-end latency under a matched device and request protocol.

The simulated gold policy is implemented in `data.py`. Approval state, source trust, sensitivity and the other typed fields are inputs, while labels and template annotations are excluded from inference. Novel wording exposes failures despite high synthetic accuracy. Deterministic permissions and approvals must remain independent of the classifier.

This is original supervised PyTorch code inspired by typed parallel decision models, not a reproduction of Jev's proprietary system. See [evaluation](EVALUATION.md) for the comparison protocol and [the measured report](FINETUNED_COMPARISON.md) for both models' results.

Old word-only checkpoints remain compatible. The original 21,306-parameter artifact is preserved at `artifacts/guard_best/model.pt`; the updated default is `artifacts/guard_scaled/model.pt`. [The experiment record](GUARD_IMPROVEMENT.md) explains data separation and validation-only iteration.
